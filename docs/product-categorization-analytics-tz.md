# ТЗ: Налаштування категоризації товарів для сторінки "Аналітика"

## 1. Мета

Забезпечити стабільну та керовану категоризацію товарів з чеків, щоб сторінка "Аналітика" коректно показувала витрати за категоріями: суму, відсоток від загальних витрат, кількість товарів, топ категорію, колір та іконку категорії.

Поточна логіка бере категорію напряму з `receipt_items.category`. Якщо в OCR або ручному введенні категорія відсутня, написана по-різному або має зайві варіації, аналітика дробиться на дублікати або потрапляє в "Інше".

## 2. Поточний стан

- Backend зберігає категорію в `ReceiptItem.category` і `Product.category`.
- API `/api/analytics/categories` групує дані за `ReceiptItem.category`.
- Якщо категорія порожня, використовується fallback `Інше`.
- Візуальні метадані категорій зараз зашиті у `CATEGORY_META` в `app/main.py`.
- OCR prompt дозволяє повертати довільний текст у полі `category`.
- Матчинг товарів через `products`, `product_aliases`, `product_match_candidates` не нормалізує категорію централізовано.

## 3. Обсяг робіт

### Входить в задачу

- Створити єдиний довідник категорій для товарів.
- Нормалізувати категорії з OCR, ручного введення та існуючих товарів.
- Прив'язати кожен товар до однієї canonical category.
- Забезпечити коректну агрегацію категорій в `/api/analytics/categories`.
- Додати механізм ручного виправлення категорії для товарів або pending match candidates.
- Підготувати міграцію або скрипт для виправлення вже збережених категорій.

### Не входить в задачу

- Повна перебудова сторінки "Аналітика".
- Побудова ML-класифікатора з навчанням на власному датасеті.
- Детальна аналітика всередині кожної категорії, якщо вона не потрібна для поточного екрану.

## 4. Бізнес-вимоги

1. Користувач має бачити на сторінці "Аналітика" узгоджені категорії без дублікатів типу `Молочні`, `молочні`, `Молочні продукти`.
2. Товари без впевненої категорії мають потрапляти в `Інше`, а не ламати відображення.
3. Одна категорія повинна мати стабільні:
   - технічний ключ;
   - назву для UI;
   - іконку;
   - основний колір;
   - м'який фоновий колір.
4. Категорія має визначатися однаково для:
   - OCR-сканування чеку;
   - ручного створення чеку через `/api/receipts`;
   - створення або оновлення товару;
   - підтвердження match candidate.
5. Адміністратор або оператор має мати спосіб виправити категорію товару, якщо OCR або авто-правило помилилося.

## 5. Довідник категорій

Базовий список canonical categories для MVP:

| Key | UI назва | Приклади товарів | Icon | Color | Soft color |
| --- | --- | --- | --- | --- | --- |
| `dairy` | Молочні | молоко, йогурт, сир, сметана, кефір | `milk` | `#16a34a` | `#eaf8ef` |
| `meat` | М'ясні | м'ясо, курка, ковбаса, фарш | `meat` | `#b45309` | `#fff1df` |
| `vegetables` | Овочі | морква, картопля, томати, огірки | `carrot` | `#f7c948` | `#fff6d9` |
| `fruits` | Фрукти | яблука, банани, виноград, цитрусові | `grapes` | `#a678e8` | `#f1e9ff` |
| `drinks` | Напої | вода, сік, кава, чай, газовані напої | `bottle` | `#2563eb` | `#e8f2ff` |
| `grocery` | Бакалія | крупи, макарони, борошно, цукор, консерви | `jar` | `#6b7280` | `#f1f2f4` |
| `other` | Інше | все, що не класифіковано | `info` | `#64748b` | `#f1f5f9` |

Категорії мають зберігатися у backend як стабільний `key`, а для UI повертатися з локалізованою назвою. Якщо для сумісності тимчасово лишається текстова назва в `receipt_items.category`, backend має нормалізувати її перед агрегацією.

## 6. Правила нормалізації

### 6.1. Вхідні значення

Нормалізація повинна приймати:

- `category` з OCR JSON;
- `category` з ручного payload `/api/receipts`;
- `Product.category`;
- `ReceiptItem.raw_name` і `ReceiptItem.item_name`, якщо категорія відсутня;
- aliases для типових OCR-варіантів.

### 6.2. Canonical mapping

Приклади мапінгу:

| Вхід | Canonical key |
| --- | --- |
| `Молочні`, `молочні продукти`, `dairy`, `milk products` | `dairy` |
| `М'ясні`, `М’ясні`, `м'ясо`, `ковбаси` | `meat` |
| `Овочі`, `овоч`, `vegetables` | `vegetables` |
| `Фрукти`, `fruit`, `банани`, `яблука` | `fruits` |
| `Напої`, `вода`, `соки`, `drinks` | `drinks` |
| `Бакалія`, `крупи`, `макарони`, `консерви` | `grocery` |
| порожньо або невідомо | `other` |

### 6.3. Пріоритет визначення категорії

1. Категорія, вручну встановлена для `Product`, має найвищий пріоритет.
2. Якщо `Product.category` порожня, використовується normalized category з item payload.
3. Якщо item category порожня, застосовуються keyword rules за `raw_name` та `item_name`.
4. Якщо правило не спрацювало, встановлюється `other`.

### 6.4. Вимоги до якості

- Регістр, апострофи, зайві пробіли та різні лапки не повинні створювати нові категорії.
- `М'ясні` та `М’ясні` мають вважатися однією категорією.
- Backend не повинен повертати в analytics категорії без `key`, `name`, `color`, `colorSoft`, `icon`.

## 7. Backend-вимоги

### 7.1. Дані

Рекомендований варіант:

- Додати таблицю або конфіг `product_categories`:
  - `key`;
  - `name`;
  - `icon`;
  - `color`;
  - `color_soft`;
  - `aliases`;
  - `keywords`;
  - `sort_order`;
  - `is_active`.
- У `products` зберігати `category_key`.
- У `receipt_items` зберігати `category_key` або нормалізовану `category`.

Мінімальний варіант для MVP:

- Винести `CATEGORY_META` і alias mapping в окремий backend-модуль.
- Додати функцію `normalize_category(category, raw_name=None, item_name=None, product=None)`.
- Викликати її у всіх місцях створення `ReceiptItem` і `Product`.
- У `/api/analytics/categories` групувати тільки за canonical key.

### 7.2. API `/api/analytics/categories`

Endpoint має повертати:

```json
{
  "analyticsSummary": {
    "title": "Покупки за категоріями",
    "subtitle": "13.04.2026 - 13.05.2026",
    "total": "₴7 542",
    "totalLabel": "Витрачено",
    "totalPeriod": "за період"
  },
  "categoryBreakdown": [
    {
      "key": "dairy",
      "name": "Молочні",
      "amount": "₴2 036",
      "percent": 27,
      "items": "147 товарів",
      "color": "#16a34a",
      "colorSoft": "#eaf8ef",
      "icon": "milk"
    }
  ],
  "topCategory": {
    "name": "Молочні",
    "categoryName": "Молочні",
    "subtitle": "13.04.2026 - 13.05.2026",
    "description": "Найбільша частка витрат",
    "amount": "₴2 036",
    "percentText": "27% від усіх витрат",
    "trend": "розраховано з реальних чеків",
    "icon": "milk"
  }
}
```

### 7.3. OCR prompt

У prompt для OCR потрібно додати жорстке правило:

- `category` має бути одним із canonical UI значень: `Молочні`, `М'ясні`, `Овочі`, `Фрукти`, `Напої`, `Бакалія`, `Інше`.
- Якщо категорія неочевидна, повертати `Інше`.

Навіть після цього backend все одно має нормалізувати значення, бо OCR не є надійним джерелом довідникових даних.

### 7.4. Ручне виправлення

Потрібен endpoint для зміни категорії товару:

```http
PATCH /api/products/{product_id}/category
Content-Type: application/json

{
  "categoryKey": "dairy"
}
```

Очікувана поведінка:

- оновити категорію в `products`;
- опціонально оновити категорію у пов'язаних `receipt_items`, якщо item був прив'язаний до цього product;
- майбутні чеки для цього товару мають використовувати виправлену категорію.

## 8. Frontend-вимоги

1. Сторінка "Аналітика" не повинна мати власної логіки визначення кольорів або іконок категорій.
2. Frontend має відображати `categoryBreakdown` так, як його повертає backend.
3. Якщо `categoryBreakdown` порожній, показувати поточний fallback або empty state без помилки JS.
4. Для категорії `other` показувати назву `Інше`, іконку `info` або наявний fallback icon.
5. Клік по рядку категорії може лишатися логом у консоль до появи деталізації категорії.

## 9. Міграція існуючих даних

Потрібен одноразовий скрипт або міграція:

1. Пройти всі `products.category` та `receipt_items.category`.
2. Нормалізувати значення до canonical key або canonical UI назви.
3. Для порожніх значень спробувати визначити категорію за назвою товару.
4. Для невизначених товарів встановити `other`.
5. Після міграції перевірити, що `/api/analytics/categories` не повертає дублікати категорій.

## 10. Acceptance criteria

- Для чеків з категоріями `Молочні`, `молочні`, `Молочні продукти` в аналітиці відображається один рядок `Молочні`.
- Для `М'ясні` та `М’ясні` відображається один рядок.
- Товар без категорії не створює порожній рядок у графіку, а потрапляє в `Інше`.
- `/api/analytics/categories?period=1m` повертає тільки категорії з довідника або `other`.
- У кожного елемента `categoryBreakdown` є `key`, `name`, `amount`, `percent`, `items`, `color`, `colorSoft`, `icon`.
- Сума `percent` по категоріях не має візуально ламати donut chart; допустиме відхилення через округлення - до 1-2%.
- Після ручної зміни категорії товару нові чеки з цим товаром потрапляють у виправлену категорію.
- Existing fallback data у `frontend/src/data/analytics.js` продовжує працювати, якщо API недоступний.

## 11. Тестові сценарії

1. Створити чек через `/api/receipts` з товарами:
   - `Молоко 2.5%`, category `молочні продукти`;
   - `Йогурт`, category `Молочні`;
   - `Куряче філе`, category `М’ясні`.
   Очікування: analytics повертає `dairy` і `meat`, без дубля `молочні продукти`.
2. Створити чек з товаром `Вода мінеральна`, category `null`.
   Очікування: category визначається як `drinks` за keyword rules або як `other`, якщо keyword rules не реалізовані для MVP.
3. Створити чек з невідомим товаром без категорії.
   Очікування: товар потрапляє в `other`.
4. Виправити категорію product через PATCH endpoint.
   Очікування: повторний запит analytics показує товар у новій категорії.
5. Передати OCR category з різним регістром і апострофами.
   Очікування: backend нормалізує значення до одного canonical key.

## 12. Рекомендована послідовність реалізації

1. Створити backend-модуль категорій з довідником, aliases і `normalize_category`.
2. Підключити нормалізацію в OCR parsed flow і ручний `/api/receipts`.
3. Оновити `/api/analytics/categories`, щоб групування йшло за canonical key.
4. Додати endpoint для ручного оновлення категорії товару.
5. Додати міграційний скрипт для існуючих даних.
6. Додати backend-тести на normalization і analytics aggregation.
7. Перевірити сторінку "Аналітика" на fallback і реальних даних.
